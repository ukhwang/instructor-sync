1. 확인된 사실: 운동 DB 테이블, published 전용 provider, 공통 검색, 버전/snapshot 기반이 존재한다. 근거는 `lib/exercises/provider.ts`, `lib/exercises/types.ts`, `supabase/migrations/20260921010000_exercise_catalog.sql` 및 기존 snapshot migration이다. 지난 실환경 보고에는 합성 완료/일부/못함 제출이 있으나 카카오 실기기·세트 타이머 검증은 남았다.
2. 위험: 회원은 휴대폰에서 조작하므로 카카오 링크·버튼·세트 진행 실패가 시연을 막을 수 있다. 지난 390px 검증은 접근성 트리 중심이라 시각적 가로 넘침까지 증명하지 않으며, READY가 모든 판매 준비 완료를 뜻하지 않는다.
3. 권장 결정: 안정성 점검 → 취약점 분류 → 수업/타이머 → 기존 운동 DB 보완 → 배포 → 실제 카카오 검증 → 피칭 리허설 순서다. 준비 시간 절감과 회원 관리 편의는 검증할 가치로 설명한다.
4. 이번 범위에서 뺄 것: 다강사·결제·가격·Pro 권한·회원 한도 변경, 질환별 자동 처방, 자동 영상 생성, 대규모 운동 수집, 매일 반복 제출 시스템, G5~G7 확장.
5. 검증 방법: 합성 회원으로 수업 기록부터 공개 제출과 다음 수업 확인까지 실행한다. 로컬 테스트·운영 적용·브라우저·실기기 결과를 나눠 기록하고 콘텐츠 검토자는 실제 검토한 사람만 기입한다.

## 2. 공통 실행 규칙

- 현재 파일과 Git 상태가 우선이다. 기존 수정·삭제·미추적 파일을 보존하고 reset/clean/일괄 덮어쓰기를 금지한다.
- 처음에 `git status --short --branch`, `AUTO_BUILD_STATE.md` 최신 부분, 관련 diff, `package.json`만 확인한다. 전체 docs 재독 금지.
- 큰 변경 전 비밀값·node_modules·.next를 제외한 복구 스냅샷을 남긴다.
- 단계 완료 시 실행 기록에 변경 파일, 명령, 결과, 미실행 이유, 다음 시작점을 짧게 추가한다.
- Supabase 작업에는 해당 스킬, SQL/RLS 작성에는 Postgres 스킬과 데이터 무결성 문서를 적용한다.
- 이미 적용된 migration을 수정하지 않는다. 필요한 경우에만 additive migration을 만들고 데이터 보존과 기능 롤백을 시험한다.
- 가격·무료 기간·권한·회원 한도·인증 구조·프로젝트 변경 금지. secrets 교체, 파괴적 변경, RLS 약화는 중단하고 보고한다.
- 운영 배포 및 합성 smoke는 기존 승인 범위를 확인해 진행한다. 계획서 자체는 실제 고객 데이터 수정이나 미검토 콘텐츠 게시 승인이 아니다.
- 운영 env 내려받기는 이전 자동 승인에서 거부됐다. 우회하거나 재시도하지 않는다. 필요한 경우 구체적 위험을 알리고 별도 승인을 받는다.
- 관련 테스트 후 다음 단계로 진행한다. 최종 배포 후보는 `npx tsc --noEmit` → `npm run verify` → `npm run build` 순서로 검사한다.
- 토큰 절약: 단계당 필요한 파일만 읽고 테스트 로그는 요약과 실패 부분만 남긴다. 전체 게이트는 최종 후보에서 실행하고 이후 코드가 바뀌면 필요한 검증을 다시 수행한다.

## 4. 단계 0 — 상태 확인과 제출 경계 보완

관련 파일: `app/h/[token]/MemberHomeworkClient.tsx`, `lib/homework-submission-draft.ts`, `lib/db.ts`, 회원 목록 오류 UI, 기존 관련 테스트.

현재 소스에서 다음을 재현하고 확인된 문제만 고친다.

- sessionStorage가 거부되면 현재 prepareSubmissionDraft는 매번 UUID를 새로 만든다. 컴포넌트 ref에 마지막 전송 payload/request ID를 유지하여 같은 페이지의 동일 내용 재시도가 같은 UUID를 사용하도록 한다. 새로고침 후 storage가 없으면 복원이 불가능함을 정직하게 기록한다.
- React state 변경 전 연속 제출을 막는 동기적 in-flight ref가 필요하다. 전송 동안 입력과 상태 전환을 잠그거나, 전송된 값과 화면 값이 섞이지 않도록 고정한 payload로 결과를 표시한다.
- `못 했어요`를 누른 후 개별 동작 체크로 쉽게 선택을 바꿀 수 있는지 확인한다. 현재 checkbox disabled로 막히는 경우, 체크하면 못함을 해제하도록 최소 수정한다.
- 복원 초안의 homework ID·UUID·불편함 범위·fingerprint 일치를 검증하고 현재 숙제에 없는 item ID는 거부한다. 손상된 storage는 안전하게 무시한다.
- 회원 목록 load 오류 문구가 등록 모달 안에만 표시되고 본문에는 빈 목록이 나오는지 확인한다. 로딩 오류 전용 표시와 재시도를 본문에 두고 오류 중 등록 판단을 막는다.
- 공개 링크 조회 실패 문구에서 `기록은 아직 제출되지 않았습니다`처럼 서버 상태를 모른 채 미제출을 단정하지 않는다. `숙제 정보를 불러오지 못했습니다. 잠시 후 다시 열어주세요`로 안내한다.

테스트: 무선택/일부/전체/못함, 못함→개별 체크, 중복 클릭, 응답 유실 후 같은 내용 재시도, 내용 변경 시 새 ID, storage 예외, 손상 초안, 서버 already_submitted 결과 재조회. 정상 empty와 조회 장애는 구분한다.

완료 기준: 재현된 결함의 회귀 테스트 통과. 이전 READY를 그대로 복사하지 않고 현재 미검증 경계를 기록한다.

## 5. 단계 1 — 의존성 취약점 분류 (P1-4)

1. 현재 package.json/lock과 실행 Node 버전을 확인한다. 기존 Vercel 로그의 19건은 당시 설치 결과이며 현재 확정 건수로 재사용하지 않는다.
2. `npm audit --json`과 `npm audit --omit=dev --json`을 실행해 결과를 로컬 보고서로 요약한다. audit의 비정상 종료 코드가 취약점 발견인지 네트워크 실패인지 구별한다.
3. 각 high/critical에 패키지, 의존 경로, advisory, 현재/수정 버전, 운영 포함 여부, 실제 호출 경로, 대응을 기록한다. npm explain으로 직접·전이 의존성을 구분한다.
4. 공식 advisory를 확인하고 실제 공격 전제와 앱 노출을 검토한다. 코드 실행·인증 우회·민감정보 노출이 현실적으로 가능한 미해결 건은 출시 차단으로 승격한다.
5. 호환 patch 범위의 필요한 패키지만 수정하고 lock 변경을 검토한다. `npm audit fix --force`, 대규모 업데이트, 쓰지 않는다는 추정만으로 인증 패키지 제거 금지.
6. 수정 후 영향 테스트와 audit 재검사. 즉시 수정 불가 항목은 이유·완화·후속 조치를 기록한다. dev-only라고 자동 안전 판정하지 않는다.

산출물: `docs/PITCH_DEPENDENCY_AUDIT.md`. 완료 기준: 모든 high/critical에 근거 있는 분류가 있고 운영 차단 건이 해결되거나 BLOCKED로 명시됨.

## 8. 단계 4 — 운동 DB 1차 구축 (P1-5)

### 4A. 기존 기반 확인

먼저 기존 catalog/types/provider/picker, seed 목록, exercise catalog/snapshot migration, `tests/exercise-catalog*.test.mjs`, `tests/homework-assignment-db.test.mjs`만 읽는다. 기존 테이블·검색·스냅샷을 재구현하지 않는다. 운영 게시 건수는 허용된 read-only 방법으로 확인하기 전 미확인으로 둔다.

### 4B. 1차 범위와 계약

목표는 기존 seed 중 약 12개를 검토 가능한 draft 데이터팩으로 정리하고, 최소 6개가 사람 검토를 통과하면 게시하는 것이다. 6개는 계획 목표이며 검토 완료 전 공개를 강제하지 않는다. 질환별 처방 목록으로 구성하지 않는다.

기존 계약을 재사용한다: 대표명, 별칭, 카테고리, 태그, 도구, 기본 cue, 반복/유지 방식, 입력 보조 기본값, media URL/alt, 출처, 버전, 게시 상태. 세트·휴식·좌우 등의 DB 누락 필드는 우선 기존 provider 기본값을 계약에 명시하고 필요성이 확인된 경우에만 additive 확장한다.

- 이름 변경에도 동일 운동을 추적하는 안정적인 운동 ID와 콘텐츠 revision을 구분한다. 현재 row ID가 버전마다 달라지고 provider가 name으로 합치는 문제를 조사한다.
- 필요하면 stable key/lineage를 additive 방식으로 보완한다. 기존 row ID와 숙제 참조는 유지한다. 단순 버전 번호 비교로 이름이 같은 별개 운동을 합치지 않는다.
- 미디어/설명은 콘텐츠 버전, 세트/횟수/휴식/개별 cue는 해당 숙제의 강사 설정이다. 회원별 수정이 공용 운동을 덮어쓰지 않는다.
- 기본값은 입력 도움이며 특정 회원에 대한 처방 또는 통증 개선 보장이 아니다.

### 4C. 콘텐츠 패키지

산출물 후보: `data/exercise-catalog/initial-drafts.json`, `docs/EXERCISE_CONTENT_REVIEW.md`, 검증/import 스크립트. 기존 동등 파일이 있으면 확장한다.

각 항목에 stable key, 이름/별칭, 움직임·도구 태그, 자세 안내 초안, 원 출처/내부 작성 근거, 미디어 권리, 검토 상태를 채운다. 검토자·검토일은 실제 확인 전 null이다. AI 초안은 검토 완료로 표기하지 않는다.

사진·영상 사용권이 불명확하면 media=null과 텍스트 안내로 둔다. 다른 서비스의 설명·영상을 무단 복사하지 않는다. 기존 fallback seed도 DB에 옮겼다는 이유만으로 검토 완료가 되지 않는다.

사용자가 확인할 항목은 동작명/설명 정확성, 일반 안내로 적절한 표현, 미디어 권리, 공개 의사다. 전문 판단을 루나가 대신 승인하지 않는다. 검토 응답이 없으면 draft 상태로 구축 완료를 기록하고 게시만 대기한다.

### 4D. 검증과 등록 도구

- dry-run을 기본값으로 하는 검증/import 도구를 만든다. 타입·빈 이름·중복 ID/버전·필수 출처·양수 반복/유지·모드 모순·URL 형식을 검사한다.
- 로컬 fixture/PGlite로 먼저 실행한다. 동일 pack 재실행은 중복 row를 만들지 않는다. 기존 published revision 내용을 upsert로 덮어쓰지 않는다.
- draft→published는 실제 검토 기록이 있어야 가능하고 범용 강사/anon에 쓰기 권한을 주지 않는다. 이번에는 관리자 웹페이지 대신 제한된 운영 스크립트 또는 기존 관리 절차를 사용한다.
- 운영 스키마·콘텐츠 적용 전에 대상 프로젝트와 diff·변경 건수·승인된 콘텐츠만 출력한다. 비밀값과 원문 회원 자료는 출력하지 않는다.
- 문제 시 새 revision을 archived로 전환하고 이전 검토된 revision으로 되돌릴 수 있게 한다. 데이터를 삭제하는 롤백 금지.

### 4E. 검색·표시·snapshot 연결

- 수업과 숙제는 기존 공통 provider를 사용한다. 예: 한글/영문 별칭, `밴드 어깨`, `매트 코어` 같은 다중 키워드 검색을 fixture로 확인한다. 검색 결과가 처방/효능 추천을 뜻하지 않도록 한다.
- DB 게시 버전 우선, legacy seed fallback은 유지하되 같은 운동 중복 표시를 줄인다. DB 실패 시 fallback 사용 사실을 표시하고 정상 DB 결과처럼 숨기지 않는다.
- 운동 선택 후 세트/횟수/개별 cue 수정이 가능하며 새 catalog 로드가 수동 입력을 덮어쓰지 않는다.
- 회원 화면은 현재 이름 기반 `getExerciseMedia(item.name)` 사용을 점검한다. 저장된 exercise_snapshot의 미디어/설명을 우선하며 snapshot이 없는 legacy 자료에만 이름 fallback을 사용한다.
- published v1로 숙제 생성 → v2 발행/이름·영상 변경 → 기존 숙제는 v1 유지, 새 숙제는 v2 사용을 검증한다.
- archived 버전은 신규 검색에서 제외되지만 과거 숙제는 열려야 한다. 재발급 시 이미 보관된 snapshot 복사와 새 처방 생성의 기존 DB 계약을 확인하고, 거부되는 경우 재선택 안내를 표시한다. 게시 제한을 우회하지 않는다.
- 원장 직접 작성 운동은 현재 숙제 항목으로 계속 지원한다. 원장 전용 재사용 운동 보관함은 별도 소유권 기능이므로 내일 범위에서 공용 catalog와 섞지 않는다.

### 4F. 테스트와 완료 정의

테스트: draft/archived 미노출, anon catalog 직접 조회 차단, authenticated published 읽기, 일반 사용자 쓰기 차단, 별칭/태그/도구 검색, 동일 import 재시도, 버전 전환, 이름 변경, 과거 snapshot 불변, DB 장애 fallback 표시, 기존 seed 호환.

운동 DB 1차 완료는 다음을 따로 기록한다.

1. 기반 구현됨: 계약·검증/import·기존 화면 연결.
2. 로컬 검증됨: 실제 관련 테스트 결과.
3. draft 자료 준비됨: 실제 작성/검증 개수.
4. 운영 적용됨: 적용한 migration/콘텐츠 수, 미적용이면 미적용.
5. 검토·게시됨: 검토 증거와 실제 published 수. 0개면 0개로 보고.

## 9. 단계 5 — 최종 Gate와 운영 배포

`npx tsc --noEmit` → `npm run verify` → `npm run build`. 실패는 이번 변경과 기존 문제로 구분하고 실패 원인과 관련 파일만 수정한다. skip은 PASS 수에 포함하지 않는다.

SQL 변경이 있을 때만 migration dry-run과 변경 목록을 확인한 뒤 기존 승인 범위에서 적용한다. 적용 이력·RLS·RPC 권한·빈 search_path를 검증한다. 이후 기존 Vercel 프로젝트에 배포하고 deployment ID/alias를 기록한다. 배포 전후 실제 계정 격리·token 만료/회수 검증 증거가 없다면 별도 미검증으로 남긴다.

합성 숙제로 생성/공개 조회/완료/부분/못함/불편함/메모/재접속 불변/강사 상세/케어 큐를 다시 확인한다. 가능한 한 필요한 소수 QA 행만 만들고 삭제하지 않는다. QA 결과를 실제 고객 성과로 설명하지 않는다.

## 10. 단계 6 — 실제 카카오톡·모바일 (P1-1)

루나: Production 390×844에서 화면 캡처와 DOM overflow를 확인한다. 긴 운동명, 키보드 표시, 3동작, 타이머, 제출 오류/완료 화면에서 가로 넘침·가려진 버튼을 확인한다. 접근성 트리만 보고 모바일 PASS를 선언하지 않는다.

사용자: 본인 휴대폰의 카카오톡 ‘나와의 채팅’에 QA 링크를 보내 직접 연다. 루나는 명시적 메시지 전송 지시 없이 대신 카톡을 보내지 않는다.

체크 순서: 링크 열기 → 로그인 없이 보임 → 운동/세트 읽기 → 첫 세트 시작 → 무음 카운트 → 휴식 → 다음 세트 → 메모 입력 중 제출 버튼 접근 → 일부 또는 못함 제출 → 재접속 수정 차단. Safari/Chrome과 카카오 WebView 결과를 구별하고 기기·OS·브라우저·시각·결과를 기록한다.

실기기 접근이나 사용자 응답이 없으면 이 항목만 MANUAL CHECK REQUIRED로 남긴다. 독립적인 코드·DB draft 작업은 끝낸다. 카카오 검증 미완료라면 피칭은 확인된 브라우저로 진행하고 카카오 지원을 검증 완료라고 말하지 않는다.

## 11. 단계 7 — 내일 5분 피칭 리허설

1. 30초: “카톡으로 보낸 숙제와 회원 답변을 다음 수업 전에 찾기 쉽게 모았습니다.”
2. 60초: 합성 회원 → 간단한 수업 기록 → 운동 검색 → 1~2동작과 세트/횟수 → 안내 초안 수정.
3. 60초: 숙제 링크 생성 → 휴대폰 공개 화면 → 첫 세트 시작/카운트/다음 세트.
4. 60초: 일부 수행·불편함·메모 제출 → 강사 상세에서 원문과 수행 동작 확인.
5. 30초: 다음 수업 준비/케어 큐 확인. 자동 건강 개선·재등록 성과를 주장하지 않는다.
6. 60초: “지금 기록을 어디에 남기시는지, 이 흐름에서 가장 번거로운 부분이 무엇인지, 실제 회원 몇 명에게 시험해보고 싶은지”를 질문한다.

새 공개 링크를 준비하고 이미 제출된 링크는 기록 보존 예시로만 쓴다. 실제 회원 정보가 화면에 노출되지 않도록 합성 회원 상세에서 시작한다. 네트워크 실패에 대비해 개인정보 없는 합성 흐름 화면을 준비하고 실제 동작과 캡처를 구별해 설명한다.

시연 동결 후 새 기능 확장을 멈춘다. 미해결 높은 위험 취약점이나 저장 오류가 있으면 실제 고객 도입을 약속하지 않고 제한된 데모 상태로 설명한다. 가격·무료 기간·25명 권한은 미확정이라고 안내한다.
