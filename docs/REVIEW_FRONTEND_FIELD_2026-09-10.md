# 운동숙제 프론트엔드·디자인·센터 운영 검토

> **문서 상태: 참고/검증 자료.** 현재 제품 결정은 `PRODUCT_BASELINE.md`, 데이터 불변조건은 `DATA_INTEGRITY_AND_POSTGRES_MIGRATION.md`를 우선한다. 이 문서의 위험·수용 기준·제안은 구현 또는 실환경 검증 완료를 뜻하지 않는다.

검토일: 2026-09-10. 역할을 나눈 AI 코드 검토이며 실제 재활센터 원장 인터뷰, 회원 관찰, 실기기 카카오톡 시험을 실시한 결과가 아니다. 제품 코드는 변경하지 않았다. 과거 기획서보다 현재 소스에 개선된 부분이 있으므로 문서의 과거 결함을 현재 결함으로 그대로 인용하지 않았다.

## 1. 현재 제품의 실제 흐름

강사는 회원의 이름·전화·잔여 수업·목표를 등록하고, 숙제를 주는 이유와 1~3개 동작을 작성한다. 만들어진 문구와 링크를 복사해 직접 카카오톡에 붙여 넣는다. 회원은 링크로 웹 화면을 열어 동작을 보고 완료/못 함, 통증 여부와 한 줄 메모를 제출한다. 강사는 다음 수업 화면에서 원문을 보고 메모를 남긴다. 잔여 4회 이하 회원은 재등록 상담 카드에 표시된다.

따라서 현재는 **카카오톡으로 전달하는 모바일 웹 서비스**다. 카카오톡 대화 안에서 응답하는 봇이나 자동 발송 서비스로 설명하면 실제와 다르다. 근거: `app/app/homework/new/page.tsx:154`, `:186`, `lib/copy.ts:41`, `app/h/[token]/MemberHomeworkClient.tsx:50`.

회원 가입이 필요 없고, 동작 수를 제한하며, 못 했다는 응답을 완료와 같은 크기로 받는 점은 도입 장벽을 줄이는 설계다. 사진/영상 수업 플랫폼을 확장하기 전에 이 짧은 기록 흐름이 반복 사용되는지 확인할 가치가 있다. 가입 장벽 감소나 반복 사용률은 아직 측정한 성과가 아니다.

## 2. 프론트엔드 개발자 판정

### 이미 개선된 코드

- 완료 상태와 통증을 단일 RPC로 제출한다(`MemberHomeworkClient.tsx:60`). 과거의 두 RPC 호출로 인한 부분 저장 경로는 프론트에서 제거됐다. 배포 DB에 해당 마이그레이션이 적용됐는지와 재시도 멱등성은 별도 문제다.
- 오디오 재개에는 2초 제한이 있고, 일시정지는 타이머와 TTS를 함께 취소한다(`VoiceCoachSession.tsx:19`, `:155`). 우측 전환 준비 3초와 휴식 0초 처리도 있다(`:244`, `:257`).
- 기본 직접 입력에 구조화된 횟수가 생기고, 15회→5회 변경 시 횟수를 다시 추론한다(`stores/homework-draft-store.ts:35`, `:139`, `lib/coach.ts:63`).

오디오는 웹 표준상도 단순 호출 성공만으로 전체 사용 경험을 보장할 수 없다. SpeechSynthesis의 speak는 큐에 넣는 API이므로 현재 코드의 설명/카운트 누적 위험을 뒷받침한다. 백그라운드 타이머는 제한될 수 있다. 이는 모든 카카오톡 버전에서 실패했다는 실측 증거가 아니다. [MDN speak](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis/speak), [MDN Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API), [MDN Web Audio 권장사항](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices)

화면 숨김 시 중단하고 복귀 후 이어서 버튼을 받는 현재 정책은 합리적인 MVP 선택이다. 다만 시작 전에 알려야 한다. 잠금화면 지속 음성을 판매 약속에 넣지 않는다. 새로고침/앱 종료 뒤 진행 복원은 아직 코드에 없으며 이 기능을 약속하지 않는다면 별도 개발 범위로 둘 수 있다.

## 3. 디자이너 판정

현재 흰색·검정·노랑과 큰 주요 버튼은 일관적이다. 그러나 화면을 실제 렌더링해 검사하지 않았으므로 대비·넘침·터치 접근성을 통과했다고 말할 수 없다. 전면 리브랜딩보다 아래 작업이 먼저다.

- 회원 첫 화면: 이름, 오늘 할 동작, 기록 남기기가 중심. ‘이번 주’와 14일 링크, 하루 기록의 관계를 명확히 한다.
- ‘다음 수업 때 강사님이 이 기록부터 확인합니다’(`lib/copy.ts:30`)는 실제 확인 프로세스가 있어야 성립한다. 확인 전/확인 완료와 확인 시간, 센터의 응답 시간 정책이 필요하다.
- 통증 체크가 있는 서비스에서 ‘기록 저장’과 ‘강사가 지금 읽음’을 구분한다. 개인정보 처리 안내와 문의 경로도 회원 화면에서 찾을 수 있어야 한다(`app/h/[token]/page.tsx`의 현재 footer에는 브랜드 문구만 있음). 실제 필요한 법적 고지·동의 범위는 보안/법률 검토 담당과 확정한다.
- 완료/못 함 버튼에는 선택 상태를 전달하는 의미 구조가 없고, textarea 라벨도 연결되지 않았다(`MemberHomeworkClient.tsx:223`, `:265`). 프리셋 선택은 클릭 div이고(`new/page.tsx:487`), 모달은 직접 만든 div이므로 키보드·초점 복귀 검증이 필요하다. semantic button/label/선택 상태부터 고친다.
- 전문용어 End State, Context Alert, 다음 챕터를 회원 목표, 수업 전 확인, 다음 목표로 바꾸는 편이 초기 교육 부담을 줄일 가능성이 있다. 이는 사용성 가설이다.

수용 시험: 320/360px 폭, 긴 한국어 동작명, 큰 글씨, 키보드가 올라온 상태, 스크린리더 선택 안내, 네트워크 실패, 만료 링크를 확인한다. 관찰자는 설명하지 않고 원장 3명·회원 5명 수준의 작은 사용성 세션부터 시작한다. 통계적 시장 검증 표본이라는 뜻은 아니다.

## 4. 재활센터 원장 관점의 운영 검토

가상의 원장 관점으로 보면 지불 가치는 ‘자동 카운트’보다 ‘수업 사이에 무슨 일이 있었는지 놓치지 않고 다음 수업 준비 시간을 줄이는 것’이다. 원장이 이미 카톡으로 직접 챙기던 회원 5~10명에 먼저 적용하면 차이를 비교하기 쉽다. 일반 소비자가 혼자 재활하는 제품으로 확장하는 것은 별도 서비스 범위다.

현재 다음 수업 화면은 가장 최근 숙제 하나만 선택한다(`app/app/session/[memberId]/page.tsx:47`). 새 숙제 이후 옛 숙제에 통증 응답이 오면 그 화면에서 묻힌다. 회원별 미확인 기록을 시간순으로 모으고, 확인 완료/담당자/후속 조치 메모를 남기는 흐름이 필요하다. 실시간 의료 모니터링으로 운영할 이유는 없지만, 원장이 언제 확인하는지와 회원이 기다려도 되는 채널인지 제품·운영 문구가 일치해야 한다.

재등록 스크립트는 실제 개선 측정이 아니다. `lib/template.ts:70`은 사용 수업 횟수를 ‘된 것’에 넣고 `:71`은 목표 달성 여부와 상관없이 아직 남았다고 말한다. `lib/copy.ts:63`의 ‘달성한 변화’ 라벨과 맞지 않는다. 또한 `lib/template.ts:48`은 단 한 번의 complete만 있어도 ‘모두 완료하셔서 다음 단계’라고 출력한다. 완료 응답은 적정한 운동 난이도·몸 상태를 평가한 정보가 아니므로 강사가 원문을 확인하고 다음 행동을 결정하도록 고쳐야 한다.

첫 판매 대상은 원장이 직접 수업하는 작은 스튜디오가 맞다. 여러 강사가 교대하는 센터에는 담당 변경, 인수인계, 계정 회수, 센터 소유권이 필수여서 지금 UI만으로 운영할 수 있다고 약속하면 안 된다. 실제 의료기관 또는 수술 후 환자 운영 적합성은 이번 역할 검토로 확인되지 않는다.

날짜 약속이나 전체 서비스 완료 견적이 아니다. 음성 코치 제외 시 프론트는 약 1~2주 작업량이지만 백엔드/개인정보/운영 출시 조건과 합쳐 전체 일정을 산정해야 한다. 코치를 유지하면 추가 1주 안팎 이상의 작업 여유가 필요할 수 있다. 제품 범위를 줄여도 다른 회원에게 잘못 연결되는 흐름, 기록 유실/중복, 미확인 통증 누락은 가볍게 취급하면 안 된다.

현재 결론: 합성 데이터 설명 시연은 가능하다. 실제 회원 파일럿은 권한·저장 P0 해결 및 두 모바일 OS의 핵심 흐름 검증 이후가 적절하다. ‘문제 없는 서비스’라는 보증 대신, 범위를 정하고 실패 시 복구 가능한 출시 기준으로 관리해야 한다.
