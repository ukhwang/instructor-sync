# 운동 카탈로그 보완 계획 — 젠스파크 검토 반영

작성일: 2026-09-22
상태: 제안·실행 전. 이번 작업은 첨부 답변과 현재 파일의 대조 및 계획 작성이다.
대상: 기존 instructor-sync. 코드·SQL·운영 DB·배포는 이번 계획 작성에서 변경하지 않았다.

## 1. 현장 검토

1. 확인된 사실: 기존 카탈로그/provider/검색/버전 snapshot 기반이 있다. `lib/exercises/provider.ts`는 DB 운동을 이름으로 합치고 기본 세트·휴식·좌우 값을 고정한다. `catalog.ts`는 seed를 일괄 published로 취급한다.
2. 위험: 콘텐츠를 늘리기 전에 ID·검토 상태·회원 전달 경계를 고정하지 않으면 이름 변경으로 운동이 합쳐지거나, 강사 참고 정보가 회원에게 전달될 수 있다. 설명 항목을 전부 회원에게 보여주면 수행 부담도 커진다.
3. 권장 결정: 동일 운동의 식별·버전·검토 계약 → 회원 전달 경로 → 소규모 자료 조사 → 사람 검토 → 검색/작성 화면 적용 순서다. 회원에게 보낼 집중 포인트는 강사가 1~2개 선택하고 수정한다.
4. 이번 범위에서 뺄 것: 질환별 자동 추천, 운동량 자동 결정, 효과 점수, 공용 DB와 원장 개인 보관함 통합, 대규모 콘텐츠 수집, 새 인증/요금/회원 한도 변경.
5. 검증 방법: 이름 변경·동명 운동·미검토 자료·영상·텍스트만 있는 운동을 합성 fixture로 확인한다. 저장 → 공개 RPC → 실제 회원 화면까지 연결해 검사하고 기존 제출 snapshot/hash 보존을 확인한다.

## 2. 젠스파크 답변의 채택·수정 판정

| 지적/제안 | 판정과 실제 수정 방향 |
|---|---|
| DB와 seed의 기본 운동량 불일치 | 채택. provider는 현재 1세트/반복당 3초/휴식 20초/좌우 false를 채운다. DB 이관 시 이를 정상 원본값처럼 취급하지 않는다. 기본값의 출처를 표시하고 실제 숙제 설정을 분리한다. |
| 별칭·태그·도구를 이름에서 추출 | 채택. 도구와 별칭을 독립적으로 작성하고 seed ID에 연결한 명시적 메타데이터를 사용한다. |
| seed 전량 published | 채택하되 단계 전환. DB 게시 상태와 legacy 노출/검토 상태를 구분한다. 과거 숙제는 유지하며, 새 공식 게시 목록에는 검토 자료만 들어간다. 기존 목록을 한 번에 지워 정상 흐름을 막지 않는다. |
| 이름 기반 버전 관리 | 채택. family ID로 동일 운동을 추적하고 기존 catalog row ID는 특정 revision ID로 유지한다. 이름만 같다는 이유로 자동 병합하지 않는다. |
| 배열 순서 기반 seed ID | 채택. 현재 seed-1…seed-40 값을 각 원본 항목에 명시적으로 고정한다. 새 slug 체계나 RPC 정규식 확대는 불필요하다. 과거 snapshot 자체가 배열 재정렬로 변하는 것은 아니지만 신규 선택/URL 연결은 잘못될 수 있다. |
| 모든 신규 필드를 즉시 추가 | 축소. 회원 안내, 강사 관찰, 검색, 검토 근거별 최소 계약을 먼저 정한다. 겹치는 canonical_name/name/slug와 primary/secondary focus는 당장 늘리지 않는다. |
| DB 검색 인덱스 다수 추가 | 보류. 현재 검색은 published 목록을 받아 브라우저에서 수행한다. aliases/equipment GIN을 추가해도 현재 브라우저 검색은 빨라지지 않는다. 서버 검색으로 전환할 때 실제 쿼리로 설계한다. |
| AI origin이면 영구 draft | 수정. 작성 출처와 검토 승인은 별개다. AI 작성 이력을 보존한 채 사람이 해당 revision을 승인하면 게시할 수 있어야 한다. |
| FK가 snapshot을 가변화한다 | 부정확. FK는 참조 무결성이고 snapshot 내용을 자동 갱신하지 않는다. 문제는 렌더링 시 최신 catalog를 다시 읽는지, UPDATE/CASCADE 정책이 무엇인지다. 이번 범위에서 새 FK를 무조건 추가할 필요도 없다. |
| 후보 12/20개의 사용 빈도·필요성 | 미확인 가설. 현재 이용 로그나 현장 조사로 입증되지 않았다. 후보 이름만 받아 먼저 원장 사용 적합성과 정확한 변형을 확인한다. |

참고: PostgreSQL 공식 제약 문서 https://www.postgresql.org/docs/current/ddl-constraints.html

## 3. 첨부 SQL을 그대로 실행하지 않는 이유

- 기존 published/archived 행은 `guard_exercise_catalog_version()`가 본문 변경을 거부한다. 제안된 canonical_name/family backfill UPDATE가 그 가드에 걸릴 수 있다. 빈 DB에서만 확인해서는 안 된다.
- `content_origin='ai'` 기본값을 기존 게시 행에도 적용한 뒤 AI는 draft만 허용하면 기존 행과 제약이 충돌한다. 기존 출처 미확인은 unknown으로 두며 AI/사람 작성으로 추정하지 않는다.
- 각 revision에 무작위 family ID를 주는 것만으로 같은 운동의 과거 버전이 묶이지 않는다. 기존 관계를 확인하는 명시적 매핑이 필요하다.
- family당 published 최대 1개 제약만으로 게시 전환이 완성되지 않는다. 기존 revision 보관과 신규 revision 게시를 하나의 관리자 트랜잭션으로 실행하고 동시 게시 충돌을 시험한다. published가 0개인 family는 허용한다.
- `default_sets=0`, reps/hold=0 허용은 현재 수행 흐름과 모순될 수 있다. 미정은 null, 세트·횟수·유지는 양수, 휴식은 0 허용으로 합의하고 앱의 실제 허용 범위와 맞춘다.
- `member_pause_note`에 강사 전용 stop_or_pause_signs 전체를 복사하면 노출 분리가 되지 않는다. 회원 문구는 별도 필드와 허용 목록으로 전달한다.
- seed ID 허용 범위와 JSON 크기를 넓혀야 한다는 근거가 없다. 새 콘텐츠는 검토된 DB revision 경로로 넣고 legacy seed 검증은 유지한다.
- 기존 UNIQUE(name, content_version)과 family 버전 계약의 충돌을 합성 데이터로 먼저 확인한다. 현재 제약을 임의 삭제하지 않는다. 실제 동명·동버전 저장이 필요해 변경한다면 별도 호환 변경으로 기록한다.

## 4. 추가로 확인한 현재 구현 누락

### 공개 RPC가 snapshot을 보내지 않음

`20260922100000_homework_public_item_requirements.sql`의 `open_homework` items는 명시적 JSON 키를 만들지만 exercise_snapshot을 포함하지 않는다. `lib/db-server.ts`는 해당 RPC 결과를 사용한다.

따라서 회원 화면 helper만 바뀌었다고 DB snapshot 미디어가 공개 링크에서 보인다고 할 수 없다. 신규 additive migration에서 회원용 snapshot projection을 반환하고 end-to-end로 확인한다. 운영 함수 정의는 이번에 조회하지 않았으므로 이 결과는 현재 저장소 파일에 대한 판정이다.

### snapshot null 미디어와 비디오 구분

`lib/exercise-media.ts`는 snapshot이 있어도 media_url이 null이면 이름 fallback을 쓴다. 또한 모든 snapshot URL을 poster로 처리한다. 새 계약에서는 snapshot의 미디어 없음도 보존하고, image/video 타입에 맞게 표시한다. 임의 확장자로 동영상 여부를 추측하지 않는다.

### 텍스트 전용 안내

`MemberHomeworkClient.tsx`는 snapshot default cue를 ExerciseMedia fallback에서만 사용하고 일반 포인트 영역은 item.cue만 표시한다. 미디어 없음·개별 cue 없음 조합에서도 검토된 회원 안내가 표시되는 테스트를 추가한다. 강사가 의도적으로 지운 값과 미입력 null을 구분한다.

이 누락 때문에 이전 보고의 “snapshot 회원 화면 연결 완료”는 부분 구현으로 해석해야 한다. 또한 이전 문서의 12개 후보 이름 목록은 검증된 JSON pack/import 도구 완성과 다르다. 해당 도구와 데이터팩은 이번 실행계획의 남은 산출물이다.

## 5. 최소 데이터 계약 제안

### A. 식별·검색

- 기존 name: 표시명으로 계속 사용. canonical_name을 중복 도입하지 않는다.
- family ID: 동일 동작·동일 변형의 개념 ID. 단순 이름/설명 변경은 같은 family의 새 revision이다.
- 기존 id/content_version: 특정 내용 버전. 다른 지지 방식·도구 등 별도 수행 변형은 별도 family로 두고 관련 운동 관계로 연결한다.
- legacy_seed_id: 확인된 동일 운동만 DB family와 연결. 이름으로 fallback 중복을 제거하지 않는다.
- aliases/tags/equipment: 명시적 배열. 선택적으로 movement_patterns/positions/body_regions를 검색 축으로 추가한다.

### B. 회원 안내

| 필드 후보 | 사용 방법 |
|---|---|
| setup_steps | 짧은 시작 자세. 상세 보기 안에서 표시 |
| execution_steps | 짧은 순서 안내. 반복 문장과 전문용어 줄이기 |
| attention_cues | 핵심 포인트 후보. 강사가 숙제에 1~2개 골라 수정 |
| member_pause_note | 회원이 읽을 수 있게 별도 검토한 중단·문의 안내 |
| media_type/url/alt | 실제 권리가 확인된 자료만. 없으면 텍스트로 진행 |
| breathing_cue | 해당 변형에서 근거·검토가 있는 경우만 입력. 없는 값은 빈 값 유지 |

회원 기본 화면은 운동명 → 강사 설정 세트/횟수/시간 → 이번 집중 포인트 → 시작 버튼 순서다. 상세 수행 순서와 영상은 펼쳐서 본다. 전 항목을 필수 입력으로 만들지 않는다.

### C. 강사 참고

- observation_points: 관찰 대상·조건·확인 방법·참고 기준을 묶어서 기록. 외부 관찰과 회원의 주관적 느낌을 구분한다.
- common_compensations: 주의 깊게 볼 패턴 후보. 모든 차이를 오류나 진단으로 판정하지 않는다.
- adjustment_options: 조정할 요소(지지/범위/부하/시간 등), 조정 설명, 적용 전제와 출처. 자동 난이도 추천은 하지 않는다.
- related_variants: 식별된 다른 운동 ID와 관계를 저장. 1차에는 관계 데이터 수집만 하고 큰 추천 시스템을 만들지 않는다.
- trainer_cautions: 회원용 안내와 별도 보관. 회원 공개 RPC에 포함하지 않는다.

관찰 기준을 저장했다고 실제 수행이 확인되는 것은 아니다. 타이머 종료·완료 버튼을 올바른 자세, 목표 달성, 건강 개선의 증거로 쓰지 않는다. 기존 회원 변화 측정 계약과도 자동 연결하지 않는다.

### D. 운동량

- DB default_sets/default_seconds_per_rep/default_rest_seconds/default_per_side 등과 provider 사이의 대응을 명시한다.
- 기본값은 입력 보조임을 작성 화면에서 알리고, 실제 값은 강사가 확인·변경해 homework item에 저장한다.
- 횟수와 유지시간의 모드 모순을 검사한다. 좌우 정보 누락을 false로 확정하지 않는다.
- 텍스트 tempo(올림/정지/내림)와 현재 타이머의 반복당 초는 동일한 모델이 아니다. 이번에 타이머를 새로 만들지 않고 자료로만 수집한다.

### E. 출처·검토

- content_origin: ai/human/mixed/unknown. 사람이 검토했다는 이유로 원래 출처를 바꾸지 않는다.
- references: URL, 자료명, 발행 기관/저자, 발행일 또는 미상, 확인일, 근거가 되는 안내 필드, 대상/변형, 한계.
- text_rights/media_rights: 근거 자료 링크와 재사용 권리는 분리한다. 링크가 있다는 이유로 설명·영상을 복사하지 않는다.
- reviewed_by/reviewed_at: 실제 사람 검토만 기록. 필요하면 review_note와 검토한 콘텐츠 hash를 함께 보존한다.
- status: draft/published/archived 유지. 검토 후 내용이 바뀌면 승인을 무효화하고 재검토한다. published는 새 revision으로 수정한다.
- snapshot_schema_version: 새 snapshot 형식 구분. exercise content_version과 별개이며 기존 homework_submissions의 snapshot.version/hash를 재계산하지 않는다.

## 6. 실행 순서와 통과 기준

### C0. 회귀 기준 및 계약 확정

현재 Git/관련 파일 확인, legacy seed ID 40개 매핑 고정, 위 회원·강사·검토 필드 계약 확정. 기존 타입/provider/store/공개 RPC/미디어 연결도를 작은 표로 남긴다.

통과: 기존 공개/생성/재발급 회귀 결과 확보, 같은 이름의 별도 운동과 이름 변경된 동일 운동 fixture 준비. 문서상의 기존 PASS를 재사용하지 않는다.

### C1. 식별·검토 상태 보완

배열 순서 기반 seed ID와 이름 기반 DB 중복 제거를 교체한다. legacy 목록에 실제 검토 상태를 표시하되 과거 숙제와 직접 작성은 유지한다. 미검토 legacy를 새 공식 게시 자료로 승격하지 않는다. 검토된 대체 자료가 준비되면 신규 선택용 legacy를 단계적으로 줄인다.

family 연결은 기존 게시 행 불변성을 훼손하지 않아야 한다. 우선 기존 row를 수정하지 않는 추가 mapping 테이블 방식을 로컬에서 검증하고, published/archived fixture에서 안전한 방법을 선택한다. 전역 trigger 해제나 RLS 완화로 우회하지 않는다.

통과: 순서 변경에도 seed ID 불변, 이름 변경 후 동일 family 유지, 동명 별개 family 비병합, 미검토 자료 게시 거부, 기존 게시·보관 행이 있는 DB에서 migration 성공. 추가 테이블은 RLS/직접 권한/관리자 경계를 검사한다.

### C2. 콘텐츠 저장과 회원 snapshot 전달

필요 필드만 additive migration으로 추가한다. capture_exercise_snapshot은 검토된 서버 원본에서 캡처하고, open_homework는 회원 허용 필드만 투영한다. 강사 전용 문구·검토자·내부 메모는 공개하지 않는다. v2 assignment와 재발급도 함께 검증한다.

UI는 snapshot 유무와 media_type을 따르고, snapshot이 있는 새 숙제에서 현재 이름 fallback으로 내용을 바꾸지 않는다. snapshot 없는 과거 숙제만 기존 fallback을 쓴다.

통과: v1 숙제 발급 → v2 이름/설명/미디어 변경 → 과거 숙제는 v1 유지. 미디어 null, 이미지, 비디오, 로드 실패, cue 빈 값, archived, 재발급, 공개 token 유효/없는/만료/회수, 다른 회원 접근, 응답에 강사 정보 없음을 검사한다.

### C3. 자료 조사와 draft pack

먼저 서로 다른 표현 구조가 필요한 기존 운동 3개로 자료 품질을 확인하고, 검토 틀이 맞으면 기존 12개로 넓힌다. 신규 20개는 수집 후보로 보관하고 동시에 게시하려 하지 않는다. 자세한 운동 설명은 조사 결과와 사람 검토 전까지 확정하지 않는다.

산출물: `data/exercise-catalog/initial-drafts.json`, JSON 검증 계약, 출처-필드 매핑, 콘텐츠 검토표. 현재 있는 12개 이름 목록을 실제 레코드로 채운다. 검토자/검토일은 null, 자료 없는 필드는 null 또는 근거 미확인으로 남긴다.

통과: 명칭/변형/장비 구분, 출처 URL과 해당 주장 대응, 배열·문자 길이·중복 ID/version·양수 운동량·mode 모순·URL/type 검사. 근거가 없다고 값을 생성하지 않는다.

### C4. draft import와 검토·게시 도구

기본 dry-run, 실제 변경 플래그 분리, 대상 기존 프로젝트/행 수/diff만 표시. 비밀값은 환경에서 읽고 출력하지 않는다. 동일 pack 재시도는 no-op, 같은 ID/version의 내용이 다르면 충돌로 거절한다. published revision을 upsert로 덮어쓰지 않는다.

draft import와 publish는 별도 동작으로 둔다. 검토자가 확인한 revision/hash와 현재 내용이 같아야 게시한다. 게시 교체는 원자적으로 실행하고 rollback은 새 revision 보관/이전 검토 revision 복귀로 수행한다. 데이터 삭제는 하지 않는다.

통과: 미검토/권리 미확인 게시 거부, 검토 후 내용 변경 시 재검토, 재실행 중복 없음, 동시 게시 충돌, 중간 오류 전체 rollback, 일반 강사·anon 쓰기 거부.

### C5. 수업·숙제 UI 적용

공통 ExercisePicker에서 운동 검색 → 상세 안내 → 이번 포인트 1~2개 선택 → 기존 숙제 작성 흐름으로 연결한다. 수업에서 선택한 운동/목적/포인트를 재사용하고 강사가 수정한 문장을 자동 덮어쓰지 않는다.

강사 화면에는 관찰·조정·출처를 펼쳐 보게 하고, 회원 화면에는 선택된 포인트와 검토된 회원 안내만 전달한다. DB 장애 fallback 표시가 picker뿐 아니라 초기 URL로 운동을 선택하는 경로에서도 유지되는지 검사한다.

통과: 한글/영문/도구 다중어 검색, 수동 운동 작성, DB 로드 실패, 비어 있는 검색, 잘못된 입력, 모바일 390px에서 장문과 영상 확인. 필드 추가가 숙제 작성 필수 입력을 늘리지 않아야 한다.

### C6. 릴리스 검증

단계별 관련 테스트 후 최종 `npx tsc --noEmit` → `npm run verify` → `npm run build`. DB migration 적용/배포는 실제 실행 요청과 기존 승인 범위를 확인한다. 이번 계획 작성은 운영 변경 요청이 아니다.

합성 회원으로 작성 → 공개 조회 → 수동 세트 진행 → 일부/못함 제출 → 수정 차단 → 강사 확인을 실행한다. 실제 Kakao 실기기와 콘텐츠 검토를 기다릴 때는 local fixture/import/retry/권한 테스트를 계속한다.

완료 보고는 기반 구현/로컬 검증/draft 수/사람 검토 수/운영 게시 수/실환경 확인을 분리한다. 운영 게시 0개도 그대로 기록한다. 별도 dependency 보안 잔여 문제는 이 운동 DB 작업으로 해결됐다고 쓰지 않는다.

## 7. 퍼플렉시티에 요청할 수정된 조사 양식

아래 요청을 운동 3개에 먼저 적용한다. DB 스키마 설계와 migration 코드는 요청하지 않는다.

> 운동숙제 서비스의 사람 검토용 자료를 조사해 주세요. 대상 운동은 [정확한 이름과 수행 변형 3개]입니다. 질환별 처방이나 회원 적합성 판정은 하지 않습니다.
>
> 운동마다 ① 대표명/별칭/변형 ② 자세/장비/움직임 검색어 ③ 시작 자세/수행 순서 ④ 회원용 집중 포인트 후보 ⑤ 강사가 직접 관찰할 항목과 조건 ⑥ 회원에게 물어 확인할 주관적 느낌 ⑦ 흔히 관찰되는 수행 차이와 조정 후보 및 적용 전제 ⑧ 회원용 중단·문의 안내와 강사용 참고사항 ⑨ 관련 변형 ⑩ 각 항목을 뒷받침하는 출처를 정리해 주세요.
>
> 출처는 대학·병원·학회·공공기관·원 연구 등 확인 가능한 원문을 우선하고, 자료 제목/기관/URL/발행일 또는 미상/확인일/정확히 뒷받침하는 항목/적용 대상과 한계를 붙여 주세요. 특정 연구 집단의 결과를 모든 회원에게 일반화하지 마세요. 참고 문헌 목록만 붙이지 말고 주장과 출처를 연결해 주세요. 자세한 설명은 원문을 복제하지 말고 요약하세요.
>
> 반복 수·세트·휴식은 보편적인 기본값으로 만들어내지 마세요. 자료에 있으면 해당 대상·목적·한계와 함께 참고값으로 기록하고, 없으면 null로 두세요. 반복당 시간과 올림/정지/내림 tempo를 구분해 주세요.
>
> 자료별 의견이 다르면 대안과 조건을 병기하고 하나의 정답으로 만들지 마세요. “근육에 힘이 느껴진다”와 같은 주관적 보고를 관찰 가능한 자세 기준으로 분류하지 마세요. 수행 기준 충족을 건강 개선으로 해석하지 마세요.
>
> 영상·사진은 참고 링크와 재사용 권리 확인을 구분하고 권리 불명은 미확인으로 표시하세요. 확인하지 못한 출처·검토자를 만들지 마세요. 모든 결과는 draft이며 reviewed_by/reviewed_at은 null입니다. 최종 결과는 운동별 표와 동일 내용의 JSON으로 주세요.

## 8. 사람이 필요한 지점

- 사용자/현장 원장: 실제 자주 쓰는 운동·변형 선택, 회원용 문구 이해도 확인, 본인 기기에서 공개 링크 사용.
- 콘텐츠 검토자: 원자료와 안내·관찰·조정 문구의 일치, 사용 조건, 권리 확인, 특정 revision의 게시 검토 기록.
- 개발 작업: 계약/식별/저장/권한/검색/snapshot/UI/import 도구와 테스트. 위 사람이 응답하지 않아도 로컬 합성 데이터로 진행 가능.

운동 후보 선정과 검토는 실제 참석·검토가 이뤄진 경우에만 완료로 기록한다.
