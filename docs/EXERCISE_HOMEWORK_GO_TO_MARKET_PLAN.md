## 1. 사업 판단과 개발 종료 기준

현재는 핵심 화면과 데이터 연결 코드가 있는 MVP 후보이며, 유료 운영 준비가 끝난 제품은 아니다. 첫 구매자는 원장이 직접 수업하는 1인 PT 스튜디오로 좁힌다. 판매 가치는 “숙제를 보내는 도구”에서 “회원의 수업 외 반응을 다음 수업과 재등록 상담의 근거로 남기는 운영 흐름”으로 바꾼다.

첫 계약은 사업체 단위로 받되 사용 계정은 원장 본인 1개다. 조직 소유권과 담당자 변경이 없으므로 여러 강사가 있는 센터에 퇴사 방지·회원 인계 기능을 약속하지 않는다. 재등록률 개선은 검증할 가설이며 판매 실적으로 주장하지 않는다.

이번 변경으로 린트 오류 2개·경고 7개를 해소했다. TrainerNav, 재등록 카드, 수업 알럿의 모든 자가 Pro 토글과 브라우저 RPC 호출 함수를 제거했고, 사라진 버튼을 안내하던 회원 화면 문구도 수정했다. Hook 의존성을 보완하고 사용되지 않는 라우터·가짜 서버 선택 인자를 제거했다. 기존 서버 데이터 조회는 lib/db-server.ts가 담당한다.

검증 결과: npx tsc --noEmit 통과, npm run lint 오류 0·경고 0, npm run build 통과. 빌드에는 기존 middleware 파일명 폐기 예정 경고가 남는다. 자동화 E2E 테스트는 없고, 연결 가능한 브라우저도 없어 실제 화면·오디오·모바일 동작은 확인하지 못했다.

로컬 함수 재현 검사: 기본 12회 및 30초 양측 동작 추론은 통과했다. 프리셋을 15회에서 5회로 수정해도 normalizeCoachItem 결과는 15회였고, 직접 입력 초안에는 구조화된 reps 값이 없었다. 이는 발견된 결함 재현이며 해당 기능 수정 완료나 DB 실행 검증이 아니다.

## 3. 모바일에서 치명적인 허점 3개

### M1. 카카오톡 인앱에서 시작 버튼과 실제 음성 시작이 분리됨

근거: [VoiceCoachSession](../app/h/[token]/VoiceCoachSession.tsx)의 unlockAudioFromGesture, [MemberHomeworkClient](../app/h/[token]/MemberHomeworkClient.tsx)의 handleStartCoach.

코드는 AudioContext.resume()을 기다린 다음 코치 화면을 연다. 생성 예외는 try 밖에 있고, resume 실패를 잡아도 재생 가능 상태를 확인하지 않는다. 대기 시간 제한도 없다. TTS 초기화와 실제 동작 설명은 비동기 경계를 지나 실행된다. 따라서 인앱 WebView 정책·중단된 오디오 상태에 따라 시작이 지연되거나, 무음인데 카운트만 진행될 위험이 있다. 모든 카카오톡 버전에서 발생한다고 확인한 것은 아니다.

회원은 자세를 잡고 화면에서 눈을 떼므로 무음 카운트는 핵심 사용 실패다. 수용 기준은 시작 제스처 내 오디오 준비, 실패/대기 시 시각 타이머로 명시적 전환, 텍스트 숙제와 기록 항상 접근 가능, 필요 시 기본 브라우저로 여는 안내다. 카카오톡 iOS/Android 각각에서 첫 실행·음소거·오디오 미지원·권한 실패를 검사한다. [MDN 오디오 재생 지침](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices)

### M2. 화면 잠금·전화·앱 전환 후 운동 진행이 끊기거나 소실됨

근거: VoiceCoachSession의 onHide, useState/useRef, startWork.

숨김 상태에서는 타이머 진행을 일시정지하고 음성을 취소한다. 이는 현재 의도된 동작이며 잠금화면 연속 오디오 기능이 아니다. 일반 일시정지 버튼은 TTS 큐를 취소하지 않아 카운트 화면이 멈춰도 말이 계속될 수 있다. 앱 프로세스 종료·새로고침·코치 닫기 뒤에는 동작/세트/좌우 진행이 복원되지 않는다. 복귀 시 resume 성공 여부도 기다리지 않고 재개한다.

수용 기준은 MVP에서 “화면이 보일 때 운동, 화면을 벗어나면 중단” 정책을 명시하고 타이머와 음성을 함께 멈추는 것이다. 복귀 후 정확한 세트·방향을 확인하고 재시작해야 한다. 진행 체크포인트를 도입한다면 최소 상태만 보관하고 링크 만료/무효화를 다시 확인한다. 잠금 중 지속 재생은 판매 약속에서 제외한다. [MDN 페이지 가시성과 백그라운드 타이머 제한](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)

### M3. 통증 기록 일부 유실과 재시도 중복이 상담 내용을 왜곡함

근거: MemberHomeworkClient.handleSubmit 및 initialLogs, [초기 SQL](../supabase/migrations/20260415000000_exercise_homework_init.sql)의 log_homework.

완료/못 함 RPC 다음에 통증 RPC를 별도로 호출한다. 첫 요청만 저장되고 두 번째가 실패하면 회원은 전체 실패 안내를 받지만 강사에게는 통증 없는 완료 기록이 남는다. 재시도하면 첫 기록이 중복된다. 버튼 disabled는 동일 요청의 응답 유실·새 창·재시도를 해결하지 못한다. 서버에는 요청 ID와 중복 제약이 없다.

카카오톡에서 링크를 다시 열면 로그가 하나만 있어도 완료 확인 화면부터 나온다. 운동 목록·코치로 돌아가려면 “기록 다시 작성하기”를 눌러야 해 매일 운동과 기록 수정이 섞인다. 기존 complete 뒤에 cant를 추가하면 요약은 정정이 아닌 “일부 완료”로 해석한다.

수용 기준은 완료 상태와 통증/메모를 한 제출로 트랜잭션 저장하고, 제출 ID로 재시도를 멱등 처리하는 것이다. append-only 원칙은 유지하되 수행일·제출 묶음·정정 대상 식별자를 정의한다. 재방문 시 운동 보기와 새 수행 기록, 기존 기록 정정을 구분한다. 첫 요청 성공/응답 유실/두 번째 실패/새로고침/다음 날 재방문을 검사한다.

## 4. 음성 카운트·세트 완주 감사

판정: 기본 자동 순서는 구성되어 있지만 회원이 자세를 바꾸며 따라 하는 흐름에는 아직 맞지 않는다. 현재 음성 코치는 파일럿의 판매 필수 기능에서 제외한다. 검증 전에는 운영에서 비활성화할 수 있어야 한다. 이번 변경에서 코치를 숨기거나 로직을 고치지는 않았다.

| 검증 시나리오 | 코드 추적 또는 실행 결과 | 필요한 수용 기준 |
| --- | --- | --- |
| 3세트 × 12회, 3초/회, 휴식 20초 | 포그라운드 지연이 없다는 가정에서 36초 운동 → 20초 휴식 → 36초 → 20초 → 36초, 총 148초 후 종료 | 마지막 횟수를 시작한 뒤 한 박자를 더 운동하는 방식임을 정의. 12회 소리 직후 조기 종료하지 않음 |
| 긴 Cue 8초, 3초/회 | startWork에서 설명과 “하나”를 큐에 넣지만 타이머는 즉시 진행. 화면은 설명 중 2·3회로 넘어갈 수 있음 | 설명 종료/건너뛰기 → 준비 → 카운트. TTS 완료·실패·시간 초과 처리 |
| 빠른 0.5초/회 | speakRepCount는 기본적으로 큐를 취소하지 않음. 발화가 박자보다 길면 밀림 | 카운트 큐 길이를 제한하고 지난 숫자를 뒤늦게 읽지 않음 |
| 30초 홀드 × 2세트 | 지연 없는 가정에서 30초 → 20초 → 30초. 설명을 듣는 동안에도 홀드 시간이 줄어듦 | 준비 후 시작, 홀드 종료와 휴식 안내 일치 |
| 좌우 동작 | 자동으로 왼쪽 → 오른쪽 → 휴식 → 다음 세트 | “오른쪽으로 바꾸세요”와 자세 전환 시간 필요. 즉시 카운트 시작 금지 |
| 휴식 0초 | normalizeCoachItem은 0을 보존하지만 advanceAfterWork의 논리 OR 기본값 처리가 20초로 바꿈 | 0초는 곧바로 다음 세트, 양수만 휴식 |
| “다음 동작” 버튼 | 실제로는 다음 세트로 이동. 마지막 세트 왼쪽에서 누르면 오른쪽을 건너뛰고 종료 가능 | 이전/다음 세트·방향·동작 의미와 버튼 이름 일치 |
| 끝내고 기록 / 자동 완주 | 둘 다 onFinished 호출. 코치 완주가 DB의 운동 완료를 자동 저장하지는 않음 | 조기 종료·건너뜀·타이머 완주를 구분하고 회원 확인 후 수행 기록 |
| 프리셋 15회 → 5회 수정 | 로컬 실행에서 화면 라벨 5회, 구조화된 reps 15 유지 | 작성·저장·화면·음성 수치를 하나의 기준으로 관리 |
| 직접 입력 12회 | 로컬 실행에서 reps 없음. 두 번째 마이그레이션의 effort_shape 제약과 충돌하는 경로 | 서버 저장 전 정규화 및 검증, 동작 저장 실패 시 숙제 전체 롤백 |

startWork의 설명과 타이머가 독립적인 점은 코드로 확인했다. 실제 발화 속도·인앱 재생 정책·블루투스 지연은 측정하지 않았다. speak()가 발화를 큐에 추가하는 동작은 [MDN 공식 API 설명](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis/speak)을 근거로 삼았다. “5초 유지”를 전체 반복 시간으로 취급하는 현재 추론도 올라가기·유지·내려오기 구분이 없어, 강사가 확인한 단순 동작만 지원해야 한다.

Pro 버튼 제거만으로 DB 권한이 보호되지는 않는다. 이번에는 DB 마이그레이션을 변경·적용하지 않았다. profiles의 행 소유권과 이용권 열 수정 권한은 별도다. 서버 과금 제한 구현 시 이를 함께 닫아야 한다. [Supabase 열 권한 문서](https://supabase.com/docs/guides/database/postgres/column-level-security)

P1: 생성 후 resetDraft 때문에 /app/session/ 경로의 회원 ID가 비는 경우, 다른 회원으로 이동했는데 이전 초안 회원이 남는 경우, 회원 등록 중복 클릭, revoke 반환 실패 무시, 클립보드 실패 안내, 다음 수업에서 미확인 과거 기록 누락을 순서대로 처리한다. 숙제 작성 효과의 의존성 경고 해소는 이런 도메인 흐름 전체를 고쳤다는 뜻이 아니다.

AGENTS.md의 기존 결정도 비판적으로 적용한다. “10초 작성”은 측정하지 않은 약속이고, Free에서 알럿을 잠그면 구매 가치를 경험하기 어렵다. “Pro=플래그만”은 과금 구현이 아니다. 이 문서의 새로운 요금 정책은 제안 사양이며 현재 코드의 Free=등록회원5명/일부 잠금과 구별한다. 회원 append-only 원칙·데모 분리·PG/CRM/LLM 미추가는 유지한다.

## 6. 원장의 지출 트리거와 현재 한계

| 구매 트리거 | 현재 제품이 못 하는 것 | 판매 순서 |
| --- | --- | --- |
| 재등록률·재등록 매출 | 카드의 “된 것”은 사용 횟수일 뿐 실제 변화가 아님. 목표 달성 여부와 무관하게 “아직”이라고 말함. 패키지 이력·상담 결과·결제일 없음 | 첫 집중 영역. 원문·강사 관찰·다음 목표로 상담 준비를 돕고 결과를 파일럿 장부로 검증 |
| 강사 퇴사 시 회원 유지 | 데이터 소유자가 auth.users인 trainer_id. 센터 조직·소유자·담당자·이관 권한 없음. 계정 삭제 CASCADE도 존재 | 현 구조로 판매 금지. 다음 단계는 센터 소유 데이터+강사 접근권한, 퇴사 시 접근 회수·인계 이력 |

원장이 카카오톡으로 이미 하던 일을 더 입력하게 만들면 비용만 늘어난다. 숙제 작성 시간과 다음 수업에서 실제 기록 확인 여부를 먼저 측정한다. 원문의 축적만으로 충성도나 재등록 인과 효과가 입증되지는 않는다.

우선 가치 증거는 “상담 전 원문을 확인하고 다음 수업에서 언급한 회원 수”다. 실제 재등록은 패키지별 만료일, 만료 후 14일 이내 재결제일, 결과 미확인 여부를 센터가 확인한 별도 장부에 기록한다. 만료+14일이 지나지 않은 회원은 분모에서 제외한다. 이전 기간과 비교하되 표본수·패키지 조건을 함께 보고하며 센터 3곳으로 인과 효과를 단정하지 않는다.

현재 오픈율은 회원 참여율로 판매할 수 없다. 링크 GET에서 opened로 바뀌므로 강사 미리보기도 집계되고, 카카오톡 미리보기 요청이 집계에 영향을 줄 가능성도 있다. 발송 확인·열람자 구분·기간 필터가 없고 revoke가 과거 상태를 덮는다. 파일럿에서는 실제 숙제를 받은 회원의 응답 유무를 센터와 확인한다.

## 7. 과금 재설계: 가격보다 유료 전환 경계를 먼저 만든다

제안 가격은 국내 구매 의사가 확인되지 않은 가설이다. 첫 3곳에는 동일 조건으로 제시하고 승낙/거절 이유를 기록한다. [Trainerize 공식 요금제](https://www.trainerize.com/pricing/)도 고객 수에 따른 요금 구분을 사용한다. 이는 과금 단위의 참고 사례이며 한국 센터가 아래 금액을 낼 근거는 아니다.

| 상품 | 제안 조건 | 전환 경계 |
| --- | --- | --- |
| Free | 원장 계정 1개, 최근 30일 숙제를 생성한 고유 회원 5명까지. 기본 조회·기록·수업 피드백 전체 경험 | 6번째 활성 회원에게 새 숙제를 만들 때 유료 필요 |
| 14일 파일럿 | 최초 3곳, 무료, 계정 1개·활성 회원 30명, 초기 세팅 1회·종료 미팅. 첫 실제 숙제 생성일부터 14일 | 시작 때 종료일과 이후 가격 고지. 무기한 연장 없음 |
| 원장 플랜 | 사업체당 월 49,000원, 부가세 별도, 계정 1개·활성 회원 30명, 월 단위 수동 청구·입금 확인 | 이용기간과 사용량은 서버에서 적용. PG 없이도 월 과금 가능 |
| 다중 강사 센터 | 지금 판매하지 않음 | 조직 소유권·이관·좌석 검증 후 별도 요금 설계 |

강사당 29,000원은 현장 방문·초기 세팅·상시 응대까지 포함하면 지원비를 감당하기 어려울 수 있다. 첫 3곳 방문은 고객 획득 실험으로 한정하고 이후는 원격 온보딩을 기본으로 한다. 지원 30분/월 × 내부 인건비 가정 30,000원/시간이면 15,000원, 가정 변동비 5,000원을 빼면 49,000원에서 29,000원이 남는다. 개발·방문·영업 고정비 전 금액이며 실제 비용으로 다시 계산해야 한다.

원장에게 제시할 경제성 예시는 센터가 직접 확인한 값만 쓴다. 가정상 추가 재등록 1건의 공헌이익이 300,000원이면 월 49,000원은 약 0.164건에 해당한다. 매출 전체를 이익으로 계산하거나 추가 재등록이 제품 때문이라고 단정하지 않는다.

### 전환을 실행할 최소 조건 (아직 미구현)

- 현재 members.length 제한을 활성 회원 제한으로 교체한다. 활성은 응답 여부와 무관하게 최근 30일 숙제를 생성한 고유 회원으로 정의한다. 취소·보관으로 당일 한도를 회피하지 못하도록 집계 이력을 보존한다.
- 6번째/31번째 회원의 숙제 생성과 이용기간 만료를 서버/DB에서 검사한다. UI 잠금·단순 is_pro·클라이언트 시간만으로 판정하지 않는다. 동시 요청도 한도를 넘지 않아야 한다.
- 계약 상태는 무료/체험/유료/만료, 시작·종료일, 허용량, 운영자 변경 이력을 필요로 한다. 운영자가 입금 확인 후 기간을 부여하며 강사는 직접 수정할 수 없다.
- 종료 3일 전·당일에 대표가 수동 안내한다. 월 이용 동의를 받으면 입금 후 활성화한다. 자동 청구로 오인시키지 않는다.
- 미결제 시 5명까지 이용하도록 전환한다. 최근 30일 활성 수가 5명을 초과했다면 새 숙제 생성은 막고, 새 계약 또는 집계 감소 후 재개한다. 이미 발급된 14일 링크의 조회·제출과 기존 기록 열람은 유지한다.
- 데이터 삭제나 통증 기록 열람 차단으로 결제를 압박하지 않는다. 계약 종료 시 반환·삭제 요청은 수동 처리 절차를 먼저 준비한다.

기술적으로 강제할 것은 유료 사용량과 기간이다. 구매 의사는 강제할 수 없다. 파일럿 시작 시 종료 미팅을 예약하고 “계속 사용하려면 월 49,000원”을 문서로 합의한다. 도입비만 받고 끝나는 형태는 반복 매출 검증이 아니므로 첫 3곳에는 선택하지 않는다.

## 9. 파일럿 성공 기준과 최종 Go/No-Go

목표는 접촉 10곳 → 데모 5곳 → 원장 운영 스튜디오 3곳 도입이다. 지표는 실험 가설이며 현재 달성값이 아니다.

- 센터별 첫 주: 실제 대상 회원 10명, 숙제 10건, 잔여 4회 이하 상담 대상 3명 확보.
- 사용성: 숙제 작성 중앙값 60초 이하, 대상 회원의 50% 이상이 최소 1회 기록. 분모와 관찰기간을 함께 보고.
- 운영 가치: 참여 센터 3곳 중 2곳 이상이 2주 연속 주 2회 이상 사용하고, 다음 수업에서 원문을 확인한 사례 3건씩 확보.
